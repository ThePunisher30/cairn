## The ideas, in plain words

**Why chunk at all.** A search engine can't return "a whole 600-line manual page" for a question about one parameter, and an embedding model can only read about 512 tokens at a time. So we cut the corpus into pieces and search over the pieces. In Phase 1 you used crude 40-line windows. Phase 2 asks: *can we cut better?*

**What "better" means.** Two things pull in opposite directions:
- **too small** and an answer gets cut across two chunks: no single chunk contains the whole answer, so no retriever can ever return it complete
- **too big** and the chunk is mostly irrelevant text, which blurs both keyword and embedding search (and may not fit the 512-token limit)

**Gold integrity (the metric of this phase).** Your questions have gold spans (file + lines). A gold span is *intact* when some single chunk contains it entirely. The **intact rate** tells you, **before any search exists**, how much damage a chunking strategy does to the answers. It's an upper bound: a retriever can't do better than the chunks allow.

**The ideas behind the three smarter chunkers**
- *Recursive:* respect paragraph breaks; only cut inside a paragraph when it's too long.
- *Heading-aware (Markdown):* a documentation page is a tree of sections. One chunk per section keeps each topic together, and the **heading path** (`Security > OAuth2 > Scopes`) is stored with the chunk so a short chunk that says "within 30 days" still carries its subject.
- *AST-based (Python):* code has structure. A function is the natural unit, so parse the file and cut at function and class boundaries instead of at a line count that lands in the middle of a function.

**Identity.** A chunk's ID is computed from its content and place (path, lines, text hash), so the same input always gives the same ID. That's what makes ingestion repeatable and, later, incremental.

**The corpus scope (a decision made here).** Phase 1's pool wrongly included translations and the repository's own tests. From now on the corpus is exactly: `docs/en/docs/**/*.md` (minus `release-notes.md`), `fastapi/**/*.py`, `docs_src/**/*.py`.

### Step 1. `src/cairn/tokens.py`: `count_tokens(text) -> int`
Chunk sizes must be measured in **tokens**, as the embedding model sees text, not in characters. You'll write an approximation with one regular expression that counts "pieces" the way a word-piece tokenizer roughly does. A token is:
1. a lowercase word, optionally with ONE capital letter in front: `Hello`, `world`, and each hump of camelCase (`camel`, `Case`)
2. a run of capitals that is not the start of the next word: `HTTP` in `HTTPException`
3. a run of digits
4. any single character that is not a letter, digit or whitespace: `,` `_` `(` `` ` `` ...

So `snake_case_name` is 5 tokens (`snake _ case _ name`), `camelCaseName` is 3, `HTTPException` is 2, `x = 42` is 3. Whitespace never counts.

Tools: `re.compile`, `|` for alternatives, `(?![a-z])` (a "lookahead": the next character must not be a lowercase letter), `pattern.findall(text)`. **Alternatives are tried left to right**, so order matters. Test: `tests/test_tokens.py`. This is an approximation of the real tokenizer (the embedding model's WordPiece), and it's what all the budgets in this phase are measured in.

### Step 2. `Document`, `Chunk`, `Chunker` and `make_chunk`
In `src/cairn/types.py` add:
- `Document(path: str, text: str, kind: str)`: frozen dataclass. `kind` is `"prose"` or `"code"`. Add a property **`lines`**: the text split into lines the way an editor counts them: split on `"\n"` only, and drop the final empty piece if the text ends with a newline. `""` gives `[]`, `"a\nb\n"` gives `["a", "b"]`, a form-feed character does **not** start a new line.
- `Chunk(id, text, path, start_line, end_line, kind, content_hash, token_count, heading_path=())`: frozen dataclass; `heading_path` is a tuple of strings. Add a property **`index_text`**: if there is a heading path, `" > ".join(heading_path) + "\n" + text`, else just the text. (That is the text a search index will use; `text` itself stays exactly the file's lines.)
- `Chunker`: a `Protocol` with `split(self, doc: Document) -> list[Chunk]`.

In `src/cairn/ingest/chunkers.py` write **`make_chunk(path, start_line, end_line, text, kind, heading_path=())`**:
- `content_hash`: SHA-256 of the UTF-8 text, as hex, **first 16 characters**
- `id`: SHA-256 of the string `f"{path}:{start_line}:{end_line}:{content_hash}"`, as hex, first 16 characters
- `token_count`: `count_tokens(text)`
- `heading_path` converted to a tuple; `ValueError` for impossible line numbers
Tools: `hashlib.sha256(...).hexdigest()`, `.encode("utf-8")`. Tests: `tests/test_chunk_types.py`.

### Step 4. The four chunkers (all in `src/cairn/ingest/chunkers.py`)
Every chunker has `split(doc) -> list[Chunk]`, builds its chunks with `make_chunk`, and uses `doc.lines` and `doc.kind`. Line numbers are 1-based and inclusive. **Chunk text is exactly `"\n".join(lines[start-1:end])`.**

**Promises every chunker must keep** (`tests/test_chunker_invariants.py` checks them on many documents): chunks are in order; a chunk never starts or ends on a blank line; every non-blank line of the document is in some chunk; ids are unique; a blank document gives `[]`; and (except overlap) no line is in two chunks.

Helper functions will make all four easier. A good set (names are yours): trim blank lines off both ends of a line range; count tokens of a line range; **pack lines greedily** into ranges under a token budget; find **paragraphs** (runs of non-blank lines).

**4a. `FixedChunker(max_tokens=200)`**, the baseline. Pack consecutive lines greedily: walk the lines keeping a running token total; when adding the next line would push the total **over** `max_tokens` *and the current chunk already has tokens*, close the chunk and start a new one at that line. A single line over budget becomes a chunk by itself. Trim blank lines from both ends of every chunk and drop chunks that end up empty. `ValueError` if `max_tokens < 1`. Test: `tests/test_fixed_chunker.py` (worked examples are in it).

**4b. `RecursiveChunker(max_tokens=200, overlap_lines=0)`**
1. paragraphs = runs of consecutive non-blank lines
2. a paragraph over budget is cut into pieces by greedy line packing (4a); one that fits stays whole
3. merge consecutive pieces while the merged range (blank lines between them included) still fits the budget
4. overlap: every chunk after the first is extended backwards to start with the last `overlap_lines` lines of the *previous* chunk, but never reaching the previous chunk's first line, then trim leading blank lines
`ValueError` for `max_tokens < 1` or `overlap_lines < 0`. Test: `tests/test_recursive_chunker.py` (its docstring restates this, with numbers).

**4c. `MarkdownChunker(max_tokens=300)`**: one chunk per section.
- A **heading** is a line that starts (column 0) with 1-6 `#` and then whitespace, **outside** fenced code blocks (a line starting, after indentation, with ``` or `~~~` opens/closes a fence).
- A **section** runs from its heading line to the line before the next heading of any level. Text before the first heading is a section with `heading_path == ()`.
- `heading_path` = the titles of the current heading and its ancestors. Keep a stack of `(level, title)`: when a heading of level L arrives, pop everything with level >= L, then push it.
- A **title** is the heading text without the `#`s and without a trailing ` { #anchor }` attribute (the docs have many).
- Trim each section's blank lines; drop empty ones. A section over the token budget is split with the paragraph logic of 4b (no overlap); all its pieces share the heading path.
Test: `tests/test_markdown_chunker.py`. Tools: `re` for the heading and anchor patterns.

**4d. `PythonChunker(fallback_max_tokens=200)`**: the AST chunker. The full rules are in the docstring of `tests/test_python_chunker.py`. In outline:
- parse with `ast.parse(doc.text)`; if it raises `SyntaxError`, fall back to `FixedChunker(fallback_max_tokens)`
- walk the module body. A **function** (`FunctionDef`/`AsyncFunctionDef`) is one chunk. A **class** becomes a *header* chunk (the `class` line, docstring, attributes, up to the first method) plus one chunk per method (nested classes recursively). **Consecutive other statements** form one chunk.
- `heading_path` is the qualified name: `("Greeter", "name")` for method `name` of class `Greeter`; `()` for module-level glue.
- **Where a chunk starts and ends:** it ends at its last statement's `end_lineno`; it starts at the first non-blank line after the previous chunk's end (so comments and decorators above a function belong to it). Trailing non-blank lines at the very end of the file are added to the last chunk.
- Tools: `node.lineno`, `node.end_lineno`, `node.name`, `node.body`, `node.decorator_list`, `isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef))`.
**Walk the sample in the test file by hand before coding it**: the expected chunks are listed there. Test: `tests/test_python_chunker.py`. Do this chunker last; it is the hardest.

Then run `tests/test_chunker_invariants.py` (it runs every chunker over six awkward documents).

### Step 5. `src/cairn/ingest/pipeline.py`
- `default_chunkers() -> dict`: `{"prose": MarkdownChunker(300), "code": PythonChunker()}`
- `ingest(root, out_path, chunkers=None, token_limit=512) -> IngestStats`: load documents, split each with the chunker for its `kind`, **sort all chunks by `(path, start_line)`**, write one JSON object per chunk to `out_path` (using your `write_jsonl`; the file is overwritten, never appended), and return the statistics. Row fields: `id, path, start_line, end_line, kind, heading_path` (a **list** in JSON), `content_hash, token_count, text`.
- `read_chunks(path) -> list[Chunk]`: the inverse (turn `heading_path` back into a tuple).
- `IngestStats` (frozen dataclass): `documents, chunks, by_kind` (dict `{"prose": n, "code": n}`), `mean_tokens, max_tokens, over_limit` (chunks with `token_count > token_limit`), `token_limit, histogram`. An empty corpus gives zeros (and an empty file).
- `token_histogram(chunks, edges=(50, 100, 200, 300, 400, 512)) -> dict`: counts per bucket, with the labels `"<=50"`, `"51-100"`, `"101-200"`, `"201-300"`, `"301-400"`, `"401-512"`, `">512"`.
- `format_stats(stats) -> str`: readable text with the document and chunk counts, mean and max tokens, the over-limit count, and the histogram.
Test: `tests/test_pipeline.py`. Make sure running ingest twice gives **identical bytes**: that means a deterministic order and no timestamps.

### Step 6. `src/cairn/evaluation/integrity.py`
- `gold_integrity(chunks, questions) -> dict` returns `{"overall": {...}, "by_category": {...}}`. Each group has `questions` (count), `spans` (count of gold spans), `spans_intact`, `span_rate` (spans_intact / spans), and `question_rate` (the share of questions **all** of whose spans are intact). A span is **intact** when some chunk with the same `path` has `start_line <= span.start_line` and `end_line >= span.end_line`. `ValueError` for no questions. `by_category` lists only the categories that appear, in `CATEGORIES` order. Index the chunks by path first so it stays fast.
- `broken_spans(chunks, questions) -> list[tuple[Question, Span]]`: the spans that are not intact, in question order. (You'll use it for failure analysis.)
Test: `tests/test_integrity.py`.
